# 20260505 会中权限策略与申请流改造方案

- Status: implemented
- Date: 2026-05-05

## 背景与问题定义

当前会中权限模型仍然偏“演示态”：

- 主持人创建会议后默认拥有全部能力。
- 普通参会者加入会议后默认只有文字聊天权限，麦克风、摄像头、共享屏幕、录制、白板、就位确认等能力都需要主持人额外授权。
- 参会者在前端点击麦克风或摄像头时，现有页面没有把“无权限”明确反馈给用户，体感上更像“点了没反应”。
- 权限申请当前只通过 `capability.request` 信令私发给主持人，其他参会者不可见，也没有统一留痕到聊天区。
- 主持人收到权限申请后，当前也缺少一个从会中消息快速跳到权限管理窗口的入口。

这套模型在当前产品目标下已经不够用，主要有两个问题：

1. **注册用户与匿名参会者没有区分**
   - 已注册用户进入会议后，仍然和匿名参会者一样默认没有麦克风、摄像头和共享屏幕能力。
   - 这导致“登录用户加入会议后默认可正常发言/开视频”的产品预期无法成立。

2. **权限申请流缺少完整交互闭环**
   - 申请前没有二次确认。
   - 申请发出后没有全员可见的系统消息。
   - 主持人侧没有可点击的快捷操作入口。
   - 申请方、主持方、旁观参会者对当前状态的理解不一致。

与此同时，近期线上还暴露出另一条独立问题：

- `TURN / coturn` 生产配置尚未真正闭环，导致桌面端与 `H5` 移动端在复杂网络下可能各自只能看到本地流。

这份方案只处理“会中权限策略与申请流”，不把 `TURN` 生产配置问题混在同一轮业务改造里；两者会并行推进，但边界必须清晰。

## 目标与非目标

### 目标

- 按“已注册用户 / 未注册参会者”区分默认能力。
- 为需要申请的能力补齐“二次确认 -> 主持人可见 -> 全员留痕 -> 快捷授权入口”的完整流程。
- 让权限不足时的前端反馈变得明确，不再出现“点击无反应”的体验。
- 保持现有主持人 / 助理 / 参会者角色模型不变，只细化默认能力分配规则。
- 为后续 `Web` 与 `H5` 两端共用同一套权限语义打下稳定基础。

### 非目标

- 本轮不改微信小程序会中能力。
- 本轮不重构 `WebRTC` Mesh 架构，不处理 `TURN` 自身部署实现。
- 本轮不把录制改成对普通参会者默认开放。
- 本轮不重新设计主持人角色体系，也不引入新的会议角色。
- 本轮不改会议持久化模型；权限申请消息仍然只保存在当前会议运行态中。

## 方案概述与核心决策

### 1. 默认能力矩阵按“注册状态”细分

会议中的默认能力按下面规则执行：

| 身份 | 默认可直接使用 | 需要向主持人申请 |
| --- | --- | --- |
| 主持人 | 全部现有能力 | 无 |
| 助理 | 维持当前实现，拥有主持人已授予的能力 | 维持当前实现 |
| 已注册参会者 | `chat`、`microphone`、`camera`、`screen_share` | `record` |
| 未注册参会者 | `chat` | `microphone`、`camera`、`screen_share`、`record` |

说明：

- “已注册参会者”指本次入会时具备真实 `userId` 且不是匿名身份的参会者。
- “未注册参会者”指通过会议号直接进入、没有系统注册身份，或显式匿名加入的参会者。
- `whiteboard`、`ready_check` 等未在本次需求中明确调整的能力，先保持现有策略，不在本轮默认放开。
- 这样可以避免本轮把“权限细化”扩大成“所有能力全面重设计”。

### 2. 能力申请前必须二次确认

当参会者尝试使用当前无权限的能力时，不直接立刻发请求，而是先弹一个确认框。

确认框至少应包含：

- 本次申请的能力名称
- 申请将发送给主持人的明确提示
- 当前参会者昵称
- “确认申请 / 取消” 两个动作

只有在参会者明确确认后，前端才发送 `capability.request`。

### 3. 权限申请需要转成全员可见的系统聊天消息

现有 `capability.request` 只私发给主持人的做法不再满足需求。新的流程应分成两层：

1. **主持人实时收到权限申请事件**
   - 继续保留即时信令能力，保证主持人可以立刻感知请求。

2. **会议聊天区追加一条系统消息**
   - 这条消息对全体参会者可见。
   - 消息文案需要明确 `@主持人`。
   - 消息需要说明：
     - 哪位参会者发起了申请
     - 申请的是哪项能力
     - 申请时间

示例文案：

- `@主持人，mister.chenlei 申请开启麦克风权限。`
- `@主持人，匿名参会者 A 申请开启共享屏幕权限。`

### 4. 系统聊天消息需要携带可点击的动作元数据

单纯文本消息无法支持“主持人点击后快速打开权限设置窗口”。因此本轮建议扩展 `ChatMessage` 的可选结构化字段，而不是依赖前端字符串解析。

建议新增的可选元数据：

- `kind`
  - `user`
  - `system`
  - `capability_request`
- `action`
  - `type`
  - `targetParticipantId`
  - `capability`
  - `requestedBy`

对外表现：

- 普通参会者看到的是一条普通系统消息。
- 主持人看到的是一条可点击系统消息。
- 主持人点击后，前端直接打开“权限与角色”窗口，并自动带入：
  - 目标参会者
  - 对应能力

这样做的原因：

- 结构稳定，避免前端靠中文文案反向解析。
- 后续如果还要做“申请已处理”“重复申请去重”“授权后消息状态更新”，可以在同一结构上继续扩展。

### 5. 主持人侧权限窗口需要支持“带上下文打开”

主持人从聊天消息进入权限窗口时，窗口不应只做普通打开，而应带着上下文：

- 自动切换到权限管理窗口
- 自动填入目标参会者 `participantId`
- 自动选中申请中的能力
- 让主持人可以直接点击授权

如果主持人已经手动打开过其他模态窗口，则应以最新的权限申请上下文覆盖旧的权限窗口输入值。

### 6. 前端对“无权限”必须有明确反馈

当前“点麦克风没反应”的体验必须消除。新的行为建议如下：

- 若该能力允许直接申请：
  - 打开确认框
- 若该能力不在本轮开放申请范围内：
  - 显示明确提示
- 若申请发送成功：
  - 显示“已向主持人发起申请”
- 若主持人已授权：
  - 显示“主持人已授权，可重新开启”

这部分属于体验修复，不改变后端权限结论。

### 7. `TURN` 生产配置单独作为并行整改项

本方案不直接修改 `TURN` 能力策略，但必须明确：

- “双方只能看到自己”的问题不能仅靠权限流改造解决。
- `TURN / coturn` 仍需按现有部署链路单独核对：
  - coturn 真实认证方式
  - 前端构建实际注入的 `VITE_MEETING_TURN_*` 或 `VITE_MEETING_ICE_SERVERS`
  - `turns:5349` 证书与域名一致性

换句话说：

- 本方案解决“为什么 H5 参会者点麦克风没反应、权限如何申请”。
- `TURN` 配置整改解决“为什么双方进会后仍然互相看不到媒体流”。

## 涉及模块 / 数据结构 / 接口 / 配置 / 存储影响

### 后端会议域

- `internal/meeting/service.go`
  - 调整 `JoinMeeting` 时的默认能力分配逻辑
  - 根据 `userId` 与 `isAnonymous` 区分注册参会者和未注册参会者
  - 新增或扩展权限申请留痕逻辑

- `internal/meeting/types.go`
  - 扩展 `ChatMessage` 结构，支持系统消息种类和可点击动作元数据

### 信令层

- `internal/signaling/hub.go`
  - `capability.request` 不能再只私发主持人
  - 需要同时触发：
    - 主持人即时事件
    - 全员可见的系统聊天消息广播

### 前端会中页

- `web/src/App.tsx`
  - 新增申请前确认框
  - 调整无权限时的点击行为
  - 让主持人可从聊天消息打开权限窗口
  - 处理新的聊天消息元数据

- `web/src/styles.css`
  - 补充确认框、可点击系统消息、主持人快捷操作态样式

### API / 会话快照语义

虽然本轮主要通过 WebSocket 完成实时交互，但 `Meeting` 快照中的 `chatMessages` 结构会变 richer：

- `GET /api/meetings/{meetingNumber}` 返回的聊天消息快照将包含新字段
- WebSocket `chat.message` 广播也会包含新字段

因此需要同步更新：

- `docs/api/README.md`

### 配置与存储

- 预计不新增数据库 schema
- 不新增部署环境变量
- 权限申请消息继续只保留在会议运行态内存中，随会议结束清理

## 兼容性、迁移方案与风险

### 兼容性

- 主持人角色不变
- 助理角色不变
- 会议创建 / 加入 / 离会 / 结束会议接口不变
- 旧会议运行态无需迁移，因为会议状态本身只在内存中保存

### 风险

1. **聊天消息结构扩展会影响前端渲染**
   - 需要保证旧的普通聊天消息仍能正常展示。

2. **主持人快捷授权入口会增加前端状态耦合**
   - 如果权限窗口和聊天窗口状态处理不当，容易出现模态切换混乱。

3. **默认能力放开后会改变产品行为**
   - 已注册参会者将首次具备默认开麦、开视频、共享屏幕能力，需确保这是明确接受的产品决策。

4. **本轮不处理 `TURN` 的话，媒体互通问题仍可能存在**
   - 即使权限申请流全部做完，若 `TURN` 配置仍不闭环，双端仍可能各自只能看到自己。

### 迁移策略

- 先在后端引入新的默认能力矩阵
- 再在前端补确认框与聊天消息动作
- 最后做桌面端创建、`H5` 加入的双端联调

## 验证与回滚思路

### 验证

#### 权限规则验证

- 已注册参会者加入会议后：
  - 可以直接开麦
  - 可以直接开视频
  - 可以直接共享屏幕
  - 录制仍需申请

- 未注册参会者加入会议后：
  - 麦克风需要申请
  - 摄像头需要申请
  - 共享屏幕需要申请
  - 录制需要申请

#### 申请流验证

- 点击受限能力时先弹二次确认框
- 确认后才真正发起请求
- 聊天区出现全员可见的系统消息
- 系统消息带 `@主持人`
- 主持人点击消息可直接打开权限窗口并自动带入目标信息
- 主持人授权后，申请方能立即获得更新后的能力状态

#### 回归验证

- 普通聊天消息不受影响
- 主持人手动打开权限窗口仍然可用
- 助理设定流程不受影响
- 会议纪要与系统消息留痕仍正常

#### 与 `TURN` 并行的生产验证

- 前端最终构建产物中的 `TURN` 地址、用户名、密码为真实值
- coturn 实际认证方式与前端注入方式一致
- 浏览器端能观察到 `relay` candidate

### 回滚

- 若新聊天消息结构导致前端异常，可先回退到“主持人私有信令 + 普通状态提示”的旧方案
- 若默认能力放开后产品反馈不符合预期，可只保留“注册用户默认开麦/开视频”，把共享屏幕重新收回申请制
- `TURN` 配置整改独立回滚，不与本方案耦合
